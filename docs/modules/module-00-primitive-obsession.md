# Module 00 — อ่านโค้ดให้เห็นกฎของธุรกิจ

บทนี้เริ่มจากคำถามธรรมดา: “บัญชีนี้ถอนเงินได้ไหม และเพราะอะไร?” ยังไม่ต้องรู้จัก ADT หรือ Functional Programming

ก่อนเรียน: ถ้าอ่าน `class`, `fun`, `val`, `var` ไม่คล่อง ให้ทำ [บทเตรียม Kotlin](../GETTING_STARTED.md) ก่อน
หลังเรียน: บอกได้ว่ากฎอยู่ตรงไหน โค้ดเปิดช่องให้ข้อมูลผิดแบบใด และควรทดสอบกรณีอะไร
เวลา: 2 sessions × 75–90 นาที • Branch: `module-00-primitive-obsession`

## 1. เรื่องที่เรากำลังจำลอง

Mini Banking System เป็นระบบบัญชีขนาดเล็กสำหรับฝึกออกแบบ ไม่ได้จำลองธนาคารจริงทุกด้าน
ในคอร์สนี้บัญชีมีรหัส ยอดเงิน และสถานะ เราตกลงก่อนว่ายอดเงินต้องไม่ติดลบ เงินฝาก/ถอนต้องเป็นบวก และถอนเงินได้เฉพาะบัญชี Active
ไม่มี overdraft, หลายสกุลเงิน หรือค่าธรรมเนียม เว้นแต่โจทย์เพิ่มเข้ามา การตกลงขอบเขตทำให้ทุกคนใช้คำว่า “ถูกต้อง” ในความหมายเดียวกัน

**Domain** คือเรื่องของงานที่โปรแกรมรับผิดชอบ เช่น บัญชี การถอน การโอน ส่วน **business rule** คือเงื่อนไขของงานนั้น เช่น “ถอนเกินยอดเงินไม่ได้”
Domain ไม่ได้หมายถึงชื่อเว็บไซต์หรือ package และ rule ไม่ได้หมายถึงข้อจำกัดที่เครื่องมือบังคับ เช่น ติดตั้ง JDK รุ่นใด

## 2. อ่านศัพท์แรกผ่านตัวอย่าง

**State** คือข้อมูลของระบบ ณ ขณะหนึ่ง เช่น บัญชี a มียอด 100 และสถานะ ACTIVE
**Invalid state** คือข้อมูลชุดที่ระบบสร้างได้ แต่ไม่มีความหมายตามกฎ เช่น ยอดติดลบทั้งที่ไม่มี overdraft
**Invariant** คือกฎที่ต้องจริงเสมอในสถานะที่เราถือว่าถูกต้อง เช่น ยอดเงินของบัญชีนี้ไม่ติดลบ คำว่า “เสมอ” รวมถึงหลังฝาก ถอน และโหลดจากฐานข้อมูลด้วย

**Primitive obsession** คือการใช้ชนิดข้อมูลทั่วไปแทนความหมายของงานมากเกินไป เช่น ใช้ `String` ทั้งกับรหัสบัญชีและสถานะ
ใน Kotlin ชื่อ primitive obsession ไม่ได้แปลว่า `String` หรือ `BigDecimal` เป็น JVM primitive ตามเทคนิค ทั้งสองเป็นชนิดทั่วไปที่ไม่บอกกฎเฉพาะของเรา

**Mutable** แปลว่าแก้ข้อมูลเดิมได้ ถ้า `balance` เป็น `var` ใครที่เข้าถึง object นี้อาจเปลี่ยนยอดเงินได้
**Side effect** คือสิ่งที่ function ทำกับโลกนอกค่าที่มันคืน เช่น แก้บัญชีที่คนอื่นถืออยู่ เขียนฐานข้อมูล หรือส่งข้อความ

## 3. Problem: โปรแกรมยอมให้สร้างอะไรบ้าง

เปิด `src/main/kotlin/io/typebanking/BankingService.kt` ใน branch ของบทนี้:

```kotlin
data class Account(
    val id: String,
    var balance: BigDecimal,
    var status: String,
)
```

อ่านทีละช่อง: รหัสเป็นข้อความใดก็ได้ ยอดเป็นเลข decimal ใดก็ได้ สถานะเป็นข้อความใดก็ได้
ถ้าเขียน `Account("", BigDecimal("-100"), "whatever")` compiler ยังรับ เพราะทั้งสามค่าเป็นชนิดที่ signature ขอไว้
**Compiler** คือโปรแกรมที่ตรวจ/แปลง source code ก่อนรัน มันรู้ชนิดข้อมูล แต่ยังไม่รู้กฎธนาคารที่เราไม่ได้เขียนลงไป

ดูการถอนต่อ:

```kotlin
fun withdraw(account: Account, amount: BigDecimal) {
    require(amount > BigDecimal.ZERO)
    check(account.status == "ACTIVE")
    check(account.balance >= amount)
    account.balance -= amount
}
```

`require`/`check` ตรวจเงื่อนไขตอนโปรแกรมทำงาน หากไม่ผ่านจะ throw exception
**Exception** คือการส่งสัญญาณผิดปกติที่หยุดการทำงานปกติของ function; คนเรียกต้องรู้ว่าจะจัดการอย่างไร
ในโค้ดนี้ amount เป็นบวกถูกตรวจทุกครั้ง และชื่อ method ไม่บอกว่าอาจ fail จากสถานะหรือเงินไม่พอ

ลอง trace ด้วยมือ: balance=100, amount=30, status=ACTIVE → ตรวจผ่านสามครั้ง → balance=70
ถ้า amount=130 → ติดที่เงินไม่พอ → ไม่ควรมีการเปลี่ยนยอด ถ้า status="ACTVE" สะกดผิด → fail แม้ตั้งใจให้ active

## 4. Impact: ปัญหาจะปรากฏกับใคร

คนทำ UI ต้องเดาว่า exception แบบเดียวกันหมายถึงอะไร คนเพิ่ม feature ใหม่ต้องจำว่าต้องตรวจ rule เดิมซ้ำที่ไหน
คนเขียน test ต้องสร้างข้อมูลผิดเองหลายแบบเพื่อดูว่าระบบจับทันหรือไม่
การตรวจหลายจุดไม่ได้ผิดเสมอไป แต่ถ้าแต่ละจุดถือกฎคนละฉบับ การแก้ requirement ครั้งหนึ่งอาจไม่ครบ

แยกกฎสามระดับเพื่อเลือกเจ้าของให้ถูก:

| คำถาม | ตัวอย่าง | จุดที่เหมาะจะรับผิดชอบ |
|---|---|---|
| อ่าน input ได้หรือไม่ | `"abc"` เป็นจำนวนเงินหรือไม่ | ขอบรับข้อมูล |
| ค่านี้เป็นค่าที่ domain ยอมรับหรือไม่ | จำนวนเงินถอนต้อง > 0 | ตอนสร้างค่าจำนวนเงิน |
| ทำงานนี้กับ state นี้ได้หรือไม่ | ถอน 130 จากยอด 100 | ตอนตัดสินใจถอน |

## 5. Before → after: วันนี้ยังไม่ต้อง refactor

ก่อน: อ่านโค้ดเป็นเพียง “มี if สามอัน แล้วลบยอด”
หลัง: อ่านเป็น “ต้องใช้เงินจำนวนบวก บัญชีต้องพร้อมถอน และยอดต้องพอ; ถ้าไม่ผ่านต้องไม่เปลี่ยนข้อมูล”
**Refactor** คือปรับโครงสร้างโค้ดโดยตั้งใจคงพฤติกรรมเดิม เราจะเริ่มทำในบท 01 หลังตั้งชื่อกฎได้ก่อน

## 6. Guided exercise — Rule hunting

1. รัน test ฝากเงินที่ให้ไว้ อ่านค่าก่อน/หลังโดยยังไม่แก้ implementation
2. เขียนตาราง rule / input ที่ผ่าน / input ที่ไม่ผ่าน / เจ้าของ rule
3. ไล่ `deposit` และ `withdraw` บรรทัดต่อบรรทัด เติมอย่างน้อย 6 แถว
4. สร้างตัวอย่าง invalid account 3 แบบ แล้วอธิบายว่าผิดเพราะอะไร ไม่ใช้เพียงคำว่า “ไม่ valid”
5. อธิบายสิ่งที่ signature `withdraw(Account, BigDecimal): Unit` บอกและไม่บอก

คำใบ้: เริ่มจากยอด 100 แล้วเปลี่ยนทีละอย่าง เช่น amount=0, amount=101, status=FROZEN
สิ่งที่ส่ง: `learning-notes/module-00.md` ของตน พร้อม rule table และกรณีที่ควรเป็น test
ผ่านเมื่อเพื่อนอ่านแล้วบอก expected behavior ของแต่ละกรณีได้โดยไม่เปิด implementation
