# คู่มือผู้เรียน — เริ่มจากสิ่งที่โค้ดต้องทำ ไม่ใช่ชื่อเทคนิค

คอร์สนี้ไม่ได้คาดหวังว่าคุณรู้จัก ADT, invariant หรือ functional programming มาก่อน เป้าหมายคืออ่านกฎของงานออก แล้วค่อยเลือกวิธีเขียน Kotlin ให้โค้ดช่วยรักษากฎนั้น

เริ่มที่ [บทเตรียมตัว](GETTING_STARTED.md) แล้วเปิด [สารบัญและเส้นทางเรียน](COURSE_INDEX.md) หากเจอคำไม่คุ้น ใช้ [ศัพท์พร้อมตัวอย่าง](GLOSSARY.md) ไม่ต้องจำทุกคำก่อนเริ่ม

## 1. เตรียมตัวก่อน session แรก

1. ทำตามขั้นตอน clone และตรวจ Java/Gradle ในบทเตรียมตัว
2. เลือก branch ของบทที่จะเรียนจาก [branch map](BRANCH_MAP.md)
3. เปิดเอกสาร `docs/modules/` ที่มีหมายเลขตรงกับ branch
4. หา Account, BankingService หรือไฟล์ domain ของบทนั้น แล้วลองชี้ว่ารหัสบัญชี ยอดเงิน และสถานะอยู่ตรงไหน
5. รันทดสอบก่อนแก้และจดผลไว้ เพื่อรู้ว่าอะไรเป็นปัญหาเดิม อะไรเพิ่งเกิดหลังแก้

```sh
git status --short
git switch module-00-primitive-obsession
gradle test
```

บท 00–10 ใช้ Gradle ที่ติดตั้งในเครื่อง ส่วนบท 11/main ใช้ `./gradlew test` กับ JDK 21 ตามบทเตรียมตัว อย่าตีความว่าข้อผิดพลาดเรื่อง Java version แปลว่า business rule ผิด

ถ้ามีงานที่ยังไม่ commit ให้เก็บงานก่อนเปลี่ยน branch ดู [วิธีเก็บและเปลี่ยนบท](#5-เก็บงานก่อนเปลี่ยนบท) ห้าม reset เพียงเพื่อให้สลับ branch ได้

## 2. เรียนหนึ่งบทอย่างไร

แต่ละบทแบ่งเป็นสอง sessions ประมาณ session ละ 75–90 นาที ไม่จำเป็นต้องอ่านรวดเดียวจบ

### Session A — เข้าใจปัญหาก่อนแก้

- อ่านคำถามเปิดบท แล้วตอบด้วยภาษาคน เช่น “ถอนเงินได้เมื่อบัญชีใช้งานได้และเงินพอ”
- อ่าน concept พร้อมตัวอย่างชีวิตประจำวัน หากศัพท์ไหนยังอธิบายเองไม่ได้ให้หยุดถาม
- อ่าน before แล้วเลือก input หนึ่งค่า ไล่ทีละบรรทัดว่าเกิดอะไร
- อ่าน after แล้วถามว่า “ทางใดที่เคยทำผิด ตอนนี้ทำผิดยากขึ้น?” ไม่ใช่แค่ “โค้ดสั้นลงไหม?”
- เริ่ม guided exercise ตามลำดับ ไม่ต้องทำ homework ใน session นี้

### Session B — พิสูจน์และทบทวน

- ให้เพื่อนอธิบายโค้ดคุณโดยไม่เปิดเอกสาร ถ้าอ่านไม่ออก ให้ปรับชื่อหรือแบ่งขั้นตอน
- ทำกรณีสำเร็จและกรณีถูกปฏิเสธ อย่าทดสอบเพียง happy path ซึ่งหมายถึงทางที่ทุกอย่างสำเร็จ
- ตอบ checkpoint โดยปิดเฉลย จากนั้นเปิด solution branch เปรียบเทียบเหตุผลและพฤติกรรม
- จดสิ่งที่เปลี่ยนจากบทก่อน เช่น “เดิม caller ตรวจ amount เอง ตอนนี้สร้าง PositiveMoney ก่อนเรียก”
- เลือก homework ที่ช่วยจุดที่ยังไม่เข้าใจ ไม่จำเป็นต้องเพิ่ม abstraction ทุกแบบพร้อมกัน

ผ่าน checkpoint 00–10 ที่ 8/10 พร้อมเงื่อนไขท้ายบท ส่วนบท 11 ใช้เกณฑ์ 16/20 และ exercise tests ครบ การผ่านคะแนนโดยยังอธิบายกฎหลักไม่ได้ไม่ถือว่าพร้อมไปบทต่อไป

## 3. เมื่อทำโจทย์ไม่ออก ให้ถามทีละชั้น

1. **ไม่เข้าใจกฎงาน?** เขียน input/output สามตัวอย่างก่อน ยังไม่ต้องตั้งชื่อ class
2. **ไม่เข้าใจศัพท์?** กลับไปนิยามใน concept และยกตัวอย่างที่ไม่ใช่ธนาคาร
3. **อ่าน Kotlin ไม่ออก?** อ่าน function signature ว่ารับอะไร/คืนอะไร แล้วอ่าน val/var, when, generic และ lambda ในบทเตรียมตัว
4. **ไม่รู้จะแก้ไฟล์ไหน?** เริ่มจาก `ModuleNNExercise.kt` ตาม guided exercise และหา type ที่มีอยู่ใน branch ด้วย IDE ก่อนสร้างชื่อซ้ำ
5. **เขียนได้แต่ผลผิด?** Trace กรณีที่ fail ด้วยมือ ใส่ค่าจริงทีละขั้น แล้วแยกว่าผิดที่สร้างค่า ตัดสินใจ หรือบันทึกผล

ตัวอย่างถามที่ช่วยให้เพื่อนตอบได้: “ผมส่ง amount=0 เข้า factory แล้วคิดว่าควรได้ error แต่ตอนนี้ได้ success; นี่คือ input และ test ที่ลอง” ชัดกว่าถามว่า “Either ใช้ยังไง?” โดยไม่มีบริบท

## 4. อ่าน test ที่ไม่ผ่านอย่างไร

Test เป็นคำถามว่าโค้ดทำตามสิ่งที่เราคาดหรือไม่ ไม่ใช่สิ่งที่ต้องทำให้เขียวด้วยวิธีใดก็ได้

| สิ่งที่เห็น | ความหมายที่ต้องแยก | สิ่งแรกที่ตรวจ |
|---|---|---|
| Java/Gradle เริ่มไม่ได้ | เครื่องมือยังไม่พร้อม | JDK/version และคำสั่งของ branch |
| unresolved reference/type mismatch | compiler อ่านชื่อหรือชนิดไม่ตรง | package, imports, signature |
| NotImplementedError | ยังมี TODO ที่ถูกเรียก | แบบฝึกของบทและขั้นตอนที่ต้องเติม |
| expected X but was Y | รันได้แต่พฤติกรรมไม่ตรง | input, rule, assertion และลำดับ checks |
| test ผ่านแต่ไม่มีกรณีปฏิเสธ | หลักฐานยังไม่พอ | เพิ่ม negative/edge cases ตามบท |

Starter 00–10 มี skeleton ที่ return Any/TODO และ tests พื้นฐาน ยังไม่ใช่ acceptance suite ครบทุกบท คุณต้องเพิ่ม tests ตามแบบฝึก อย่ารักษา Any ไว้เพียงเพราะเป็นชนิดที่ให้มาตอนแรก

บท 11 แยกชัด: `./gradlew test` ตรวจ baseline ที่ต้องผ่าน; `./gradlew exerciseTest` ตรวจ TODO ที่ตั้งใจให้ไม่ผ่านก่อนทำ หาก suite นี้ผ่านตั้งแต่ยังไม่ได้แก้ ให้ตรวจว่ากำลังอยู่ใน starter และ branch ที่ถูกต้อง

## 5. เก็บงานก่อนเปลี่ยนบท

เอกสารทุกบทอยู่ในทุก branch เพื่อเปิดอ่านได้ แต่ **โค้ด** เปลี่ยนตาม branch เลือก branch ของบทเมื่อทำแบบฝึกจริง

สร้าง branch ส่วนตัวจากบทที่เลือก เพื่อไม่เผลอแก้ course branch:

```sh
git switch module-01-value-objects
git switch -c my-learning/module-01
git add src docs
git commit -m "Practice module 01 value objects"
```

เลือกชื่อ branch ของตัวเองได้ `git add src docs` ใช้เมื่อได้ตรวจแล้วว่าไฟล์ในสองโฟลเดอร์นี้เป็นงานที่ต้องการเก็บ ไม่มีข้อมูลลับปะปน หลัง commit แล้วจึงสลับไป course branch ถัดไป

หากอยากพักงานชั่วคราว ใช้ `git stash push -u -m "module 01 work"` แล้วตรวจ `git stash list` เมื่อกลับมาใช้ `git stash apply` ซึ่งยังเก็บสำเนา stash ไว้ หากเกิด conflict ให้แก้ก่อนลบสำเนา หลีกเลี่ยง reset/clean และอย่าใช้ script reset โดยยังไม่อ่านคำเตือน

เพื่อเห็น progression ให้เทียบ branch ของบทก่อนกับบทปัจจุบัน แล้วแยกการเปลี่ยนเอกสารออกจาก source code:

```sh
git diff module-01-value-objects..module-02-adt -- src
```

บาง snapshot มีแนวคิดจากบทถัดไปมาแล้ว เพื่อเรียนอย่างต่อเนื่องให้โฟกัส exercise และหัวข้อปัจจุบัน ไม่ต้องแก้ทุกไฟล์หรือเข้าใจ abstraction ทั้งโปรเจกต์ทันที

## 6. ทำงานเป็นคู่โดยไม่ปล่อยให้คนหนึ่งทำทั้งหมด

สลับคนพิมพ์กับคนอ่านกฎทุก 10–15 นาที คนอ่านต้องเลือก test case และทายผลก่อนรัน คนพิมพ์ต้องอธิบายว่าบรรทัดที่แก้ช่วยกฎใด ไม่ใช่แค่เล่า syntax

ก่อนเปิดเฉลย ทั้งคู่ต้องตอบได้ว่า input ใด valid, input ใดถูกปฏิเสธ, โค้ดส่วนใดเป็นเจ้าของกฎ และจะใช้ test ตรวจอย่างไร เมื่อคำตอบต่างกันให้คุย requirement ก่อนแก้โค้ด

## 7. สิ่งที่ส่งท้ายบท

- โค้ดและ tests ของ exercise ตามรายการในบท
- คำตอบ checkpoint พร้อมเหตุผล ไม่ต้องใช้คำอังกฤษครบทุกคำ
- ตัวอย่างก่อน/หลังหนึ่งกรณีที่เห็นพัฒนาการจริง
- บันทึกสั้น ๆ: กฎที่ type ช่วยได้, กฎที่ยังต้องตรวจตอนรัน, คำถามที่ยังไม่ชัด

เก็บบันทึกในพื้นที่เรียนของคุณ เช่น `notes/module-01.md` ไม่ต้อง push ขึ้น course repository กลางเว้นแต่ทีมตกลงไว้ เฉลยเป็นจุดเปรียบเทียบ ไม่ใช่ implementation เดียวที่ถูกต้อง: แบบอื่นใช้ได้ถ้ารักษากฎ มี contract ชัด และผ่าน tests ที่เหมาะสม
